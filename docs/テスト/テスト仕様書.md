## 2. 前提

本書は、要件定義書・API設計書・テーブル定義書・コーディング規約に基づき、バックエンド（Laravel 13 / PHP 8.5）のテスト仕様を定義する。

### 2.1 テスト対象の範囲

| 対象                           | 含む/除く |
| ------------------------------ | --------- |
| 認証API（登録・ログイン・ログアウト） | 含む |
| 家計簿レコードAPI（CRUD）      | 含む      |
| 自己レビューAPI（CRUD）        | 含む      |
| スレッド・AIメッセージAPI      | 含む      |
| 基準値設定API                  | 含む      |
| ユーザー情報API（編集・退会）  | 含む      |
| マスタデータAPI                | 含む      |
| AIフィードバック生成処理（Python worker） | **除く** |

AIフィードバック生成処理（Python worker による外部AI API呼び出し）は本テスト仕様の対象外とする。スレッド・AIメッセージAPIについては、Laravel 側の投稿作成・一覧取得・ステータス管理のみをテスト対象とする。

### 2.2 背景・関連Issue

本テスト仕様書の作成にあたり、以下の経緯と既知の課題を考慮している。

#### アーキテクチャの経緯

- PR #50 で Controller → Service → Repository のレイヤー分離を導入。テスタビリティが大幅に向上した
- PR #51 でスレッド・AIメッセージAPIを実装。排他ロックによる F-008 重複防止が正しく機能している

#### 開発過程で検出・修正済みの課題

| # | 課題 | 修正内容 | テストでの扱い |
|---|------|---------|----------------|
| 1 | `findOrFail()` が読み取り専用パスでも `lockForUpdate()` をかけていた | `findOrFail()`（ロックなし）と `findOrFailForUpdate()`（ロックあり）に分離 | テストでは両メソッドの使い分けを検証する |
| 2 | `SelfReviewService::create()` にトランザクションがなかった | `DB::transaction()` で囲む形に修正 | 結合テストで親レコード削除との競合を検証する |
| 3 | `details` 未送信時に Undefined array key が発生しうる状態だった | `KakeiboRecordStoreRequest` で `required` に修正 | バリデーションテストで details 未送信時の 422 を検証する |
| 4 | `UserService::destroy()` のパスワードチェックがトランザクション外だった | トランザクション内に移動 | 結合テストでパスワード照合タイミングを検証する |
| 5 | parentId 不正時のステータスコードが設計書と異なっていた（404 vs 422） | 存在チェックを FormRequest から Service 層に移動し 404 を返すよう修正 | 結合テストで 404 レスポンスを検証する |

### 2.5 Git 運用方針（テスト作業時）

テスト作業中のブランチは、**コミットまたはマージを行うたびに必ず push する**。ローカルだけにコミットが溜まった状態にしない。

```bash
# コミット後
git push

# develop を merge した後
git push
```

### 2.6 テスト実行方法

#### PHPUnit（単体テスト・結合テスト）

```bash
# 全テスト実行
docker compose exec backend php artisan test

# 単体テストのみ
docker compose exec backend php artisan test --testsuite=Unit

# 結合テストのみ
docker compose exec backend php artisan test --testsuite=Feature

# 特定のテストクラス
docker compose exec backend php artisan test --filter=RegisterTest

# 特定のテストメソッド
docker compose exec backend php artisan test --filter=RegisterTest::test_register_success
```

#### .http ファイル（APIテスト）

JetBrains IDE（PhpStorm 等）または VS Code の REST Client 拡張で実行する。

### 2.7 テスト失敗時の取り扱い

テストが失敗した場合、以下の手順で対応する。

#### 手順1: 失敗内容を確認する

失敗したテストの出力から、以下の情報を確認する。

- どのテストが失敗したか（テストクラス名・メソッド名）
- 期待結果と実際の結果の差分（`Expected ... but got ...`）
- エラーメッセージやスタックトレース

```bash
# 失敗したテストだけを再実行して詳細を確認する
docker compose exec backend php artisan test --filter=失敗したテストクラス名
```

#### 手順2: 原因を切り分ける

失敗の原因は大きく2つに分かれる。

| 原因 | 判断基準 | 例 |
|------|---------|-----|
| **テストコードの不備** | 仕様書やAPI設計書と照らし合わせて、テスト側の期待値が間違っている | テストが `200` を期待しているが、設計書では `201` が正しい |
| **実装側のバグ** | テストの期待値は仕様書通りだが、実装がそれを満たしていない | 設計書では `404` を返すべきだが、実装が `422` を返している |

迷ったら、仕様書（テスト仕様書・API設計書・要件定義書）を基準にする。

#### 手順3: 修正する

**テストコードの不備だった場合:**

テストブランチ上で直接修正する。

1. テストコードを修正する
2. 仕様書の該当テストケースにも誤りがあれば、仕様書も合わせて更新する
3. 修正したテストが通ることを確認する
4. テストブランチにコミット・push する

**実装側のバグだった場合:**

テストブランチとは別の fix ブランチで修正し、修正後にテストブランチへ取り込む。

1. GitHub Issue を起票する（テストID・再現手順・期待結果・実際の結果を記載）
2. テストブランチの作業を一旦コミットしておく（テスト失敗のままで OK）
3. develop から修正用ブランチ（`fix/担当者/内容`）を切り、実装を修正する
4. 修正を PR 経由で develop にマージする
5. テストブランチに develop の修正を取り込む
   ```bash
   git switch feature/担当者/テストブランチ
   git merge develop
   git push
   ```
6. 該当テストが通ることを確認する

#### 手順4: 回帰テストを実行する

修正後は、該当テストだけでなく関連するテストスイート全体を再実行して、修正が他のテストを壊していないことを確認する。

```bash
# 単体テスト全体
docker compose exec backend php artisan test --testsuite=Unit

# 結合テスト全体
docker compose exec backend php artisan test --testsuite=Feature

# 全テスト
docker compose exec backend php artisan test
```

#### マージ判断

失敗しているテストがある状態での develop へのマージは原則行わない。

ただし、既知の未実装機能（Python worker 等）に起因する失敗で、テスト側を `markTestSkipped()` で明示的にスキップしている場合は例外とする。
